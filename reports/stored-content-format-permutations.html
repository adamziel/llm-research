Report 004 · Storage-only field guide

Stored content format permutations

How WordPress site builders actually layer JSON, block comments, HTML, CSS, shortcodes, base64, PHP serialization, and cross-record references—before anything is rendered.

5 August 2026 · Scope: canonical builder data, post content, post meta, options, public exports, and documented save formats · Rendered DOM and frontend caches excluded

Not one format or the other

Each database value has an outer storage grammar, but fields inside it can carry additional grammars. A JSON page can hold HTML, CSS, a shortcode, or an encoded builder token. WordPress block markup deliberately combines JSON attributes in comments with saved HTML. A shortcode can contain base64 that decodes to JavaScript. A PHP-serialized array can contain byte-counted HTML.

The practical unit is therefore a storage chain: start with the outermost grammar, then descend only through fields whose schema defines another grammar.

JSON storage chains

Elementor and Oxygen demonstrate that “plain JSON” is only a statement about the outer envelope. Their JSON values can still contain code, markup, encoded settings, and reference graphs. The Oxygen source material is component/clipboard and selector-export JSON: it proves those export shapes and UUID links, not the private SQL or post-meta envelope.

01

JSON element tree

JSON → elements[] → settings + children

Elementor stores page configuration and content as JSON in post meta; Oxygen exports element records with nested children.

Documented Elementor data structure · Observed public Elementor/Oxygen exports

02

JSON repeater and object arrays

JSON → settings → items[] → item fields

Slides, tabs, links, breakpoint settings, and other repeaters introduce additional object/list layers without changing the outer grammar.

Observed public Elementor templates

03

Media object with ID and URL

JSON → media → id + url

A resource is not always represented by one URL. Elementor commonly keeps the attachment ID beside it.

Media object with size map

Oxygen exports preserve the primary URL plus per-size URLs and metadata, producing several migration targets for one attachment.

05

HTML string inside JSON

JSON → settings.editor → HTML

Elementor Text Editor and rich-description fields store literal HTML strings inside the JSON document.

06

HTML containing inline SVG

JSON → settings.html → HTML → <svg> descendants

A public Elementor HTML-widget template stores form controls and literal SVG elements in the JSON string.

07

Raw CSS string

JSON → custom_css → CSS selectors + declarations

Public Elementor and Oxygen exports contain unparsed CSS strings, including pseudo-classes, custom properties, functions, and keyframes.

Observed Elementor and Oxygen exports

08

Structured CSS values

JSON → property → number + unit + formatted style

Oxygen can store both a typed value and its CSS spelling. These values must remain internally consistent.

Observed Oxygen 6 selector export

09

Variable and UUID tokens

JSON → CSS-like field → {var-UUID}

The string is a builder reference token, not ordinary CSS custom-property syntax. It resolves through a separate reference graph.

Observed Oxygen 6 selector export

10

Shortcode inside JSON

JSON → settings.shortcode → WordPress shortcode

Public Elementor exports store third-party shortcode text as the value of a widget setting.

Dynamic tag with encoded JSON

JSON → [elementor-tag … settings="%7B…%7D"] → percent-decoded JSON

An actual _elementor_data dump shows a shortcode-like Elementor token whose attribute contains percent-encoded JSON settings.

Observed public Elementor replacement issue

12

JSON component plus separate selector export

component export JSON ⇢ selector export JSON → classes + breakpoints + variables

Oxygen’s public component and selector exports expose linked UUIDs across two JSON representations. They do not establish the exact database envelope.

Observed two public Oxygen 6 exports

Block markup storage chains

The block editor’s canonical representation is intentionally hybrid. The 30 inspected core and Otter registered patterns are natural vendor/core pattern source saved and read through WordPress—not generated content fixtures.

13

Dynamic block comment

post_content → <!-- wp:name {JSON} /-->

A self-closing block may contain JSON attributes with no saved HTML of its own.

Observed 16 of 30 inspected patterns

14

Static block hybrid

comment JSON + saved HTML + closing comment

The JSON attribute representation and HTML representation coexist in one post_content string.

Observed all 30 patterns · Documented WordPress handbook

15

Nested block hybrids

block JSON + HTML → nested block JSON + nested HTML → …

Every inspected pattern nested additional block delimiters inside the outer block’s saved HTML region.

Observed all 30 patterns

16

Structured style plus inline CSS

comment JSON.style + saved HTML.style="CSS"

The same design intent can appear as a nested JSON style object and as generated inline declarations in the saved block HTML.

Observed both representations in 17 patterns

17

Preset token plus CSS custom property

JSON: var:preset|spacing|50 + HTML: var(--wp--preset--spacing--50)

WordPress serializes the editor-side preset token and its CSS spelling differently within the same block representation.

Observed 14 patterns

18

URL duplicated across representations

comment JSON.url + saved HTML <img src="…">

Image, cover, embed, and custom-block patterns may preserve one resource in both the block attributes and the saved HTML.

Observed core and Otter patterns

block delimiter → literal HTML payload

The block grammar wraps an explicitly HTML-valued body. WordPress identifies this as a static block saved directly in post content.

block delimiter → shortcode text

Shortcode storage chains

WPBakery documents its shortcode parameter encoding, and a natural public page-layout source exposes the extra percent-encoding layer used by a real vc_raw_html payload.

Base64 and percent-encoded raw HTML

WPBakery shortcode → base64 → percent-encoded text → HTML

A public vc_raw_html source requires base64 decoding followed by URL decoding before it becomes HTML.

Observed public WPBakery layout source · Documented WPBakery parameter API

Base64 raw JavaScript

WPBakery shortcode → base64 → JavaScript

The documented textarea_raw_html parameter type is intended for raw JavaScript as well as raw HTML.

Serialized and multi-record storage

Some builders add another constraint: values are either protected by PHP serialization byte counts or distributed across multiple database records that must stay synchronized.

23

PHP-serialized element arrays

PHP serialization → elements[] → settings

Bricks documents serialized element arrays in three page-area post-meta keys.

Documented Bricks data model

24

Serialized flat parent graph

PHP serialization → elements[] → id + parent + children[]

Bricks stores flat element records with relationship fields, combining serialization integrity with graph integrity.

Documented Bricks data model

25

Serialized page plus serialized global stores

serialized page data ⇢ separately serialized wp_options

Bricks stores classes, variables, theme styles, palettes, breakpoints, and components separately. References differ: classes and component instances use IDs, variables use CSS custom properties, breakpoints use key suffixes, and theme styles use conditions.

Documented Bricks data model

26

Canonical HTML in post meta

tve_updated_post → Architect HTML

Thrive identifies this field—not a rendered page response—as the canonical Architect layout source.

Documented Thrive Architect REST API

27

HTML plus optional coordinated CSS and state

HTML meta + optional CSS + globals + events + simplified content

An editor-equivalent Thrive save can include canonical HTML, editor/user CSS, globals, events, feature flags, symbol IDs, and stripped/simplified content used for post_content migration paths. Not every field is present on every page.

Documented Thrive Architect REST API

28

Elementor template referenced by a block

block attributes.selectedTemplate ⇢ Elementor template post → _elementor_data JSON

The official dynamic block stores a numeric template-post ID in selectedTemplate; the Elementor document lives in that template post’s metadata.

Documented Elementor Blocks for Gutenberg 1.1.5 source

Source-confirmed boundary cases

Real feature paths still awaiting a natural public stored artifact

Elementor 3.26 can render Gutenberg blocks alongside Elementor widgets, but the available sources define separate inputs—_elementor_data JSON and block markup in post_content—not block comments nested inside a Text Editor setting. No naturally authored public record demonstrating settings.editor → block markup was found, so that permutation is excluded.

Likewise, controlled Beaver Builder and SiteOrigin saves verified their serialization paths, but their populated values were fixtures. Those paths are not counted among the permutations above.

What was deliberately excluded

  • Every frontend-rendered DOM fragment and every signal found only after rendering.
  • Generated CSS files and HTML caches unless the vendor identifies them as canonical authoring data.
  • Hypothetical PHP-serialization examples not emitted by a real builder save path.
  • Controlled fixture values as proof of prevalence or naturally authored content.
  • Claims that an add-on inherits every storage behavior of its parent builder without a stored artifact or vendor source.

The permutation set is not mathematically finite: raw HTML/code controls can hold arbitrary sublanguages. The 28 entries above are the materially distinct storage paths substantiated by current public artifacts or explicit vendor storage documentation.
